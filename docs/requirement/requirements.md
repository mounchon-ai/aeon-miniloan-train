## หลักการสำคัญของโปรเจกต์

- **Claude Code เป็นผู้เขียนโค้ดทั้งหมด** ผู้เรียนไม่ต้องเขียนโค้ดเอง
- **บทบาทของผู้เรียน = กำกับการผลิต + ทดสอบ** เปรียบเหมือน Product Owner ที่กำหนดว่าจะให้สร้างอะไร + QA ที่ตรวจว่าของที่ได้ถูกต้องไหม โดยมี Claude Code เป็นทีมพัฒนา
- ดังนั้น requirement ทั้งหมดเขียนใน**เชิงพฤติกรรมที่สังเกต/ทดสอบได้** (behavioral & testable) ไม่ระบุวิธี implement ภายใน — ให้ Claude Code เลือกวิธีตามภาษา/เฟรมเวิร์กที่ผู้เรียนกำหนด
- เกณฑ์ความสำเร็จวัดจาก **Acceptance Criteria** ในเอกสารนี้ ไม่ใช่จากโค้ดที่เขียนด้วยภาษาใด

## 1. เป้าหมายปลายทาง (End Goal) — เริ่มจากตรงนี้

> ระบบให้ผู้สมัครยื่นขอสินเชื่อส่วนบุคคล ระบบประเมินตามกฎที่กำหนด เจ้าหน้าที่อนุมัติ/ปฏิเสธ เมื่ออนุมัติและเบิกจ่ายแล้วระบบสร้างบัญชีสินเชื่อพร้อมตารางผ่อนแบบลดต้นลดดอก บันทึกการชำระรายงวด และปิดบัญชีได้ (รวมถึงปิดก่อนกำหนด)

ถอยกลับจากเป้าหมายนี้ เราต้องมีความสามารถ 4 กลุ่มใหญ่:

1. **รับและประเมินใบสมัคร** (Origination)
2. **อนุมัติและเบิกจ่าย** (Approval & Disbursement)
3. **สร้างบัญชีและตารางผ่อน** (Servicing setup)
4. **รับชำระและปิดบัญชี** (Servicing operation)

## 2. ขอบเขต (Scope)

### อยู่ในขอบเขต (In Scope)
- **แยกเป็น 2 ส่วนที่ deploy แยกกัน: Backend API (ให้บริการ business logic ทั้งหมด) + Web (client ที่เรียกใช้ API)**
- สินเชื่อส่วนบุคคลแบบผ่อนชำระเท่ากันทุกงวด (installment loan)
- ดอกเบี้ยแบบลดต้นลดดอก (reducing balance)
- Workflow อนุมัติแบบ 1 ระดับ (เจ้าหน้าที่พิจารณา 1 คน)
- การชำระเงินแบบบันทึกด้วยมือ (mock payment — ไม่เชื่อม payment gateway จริง)
- ปิดบัญชีก่อนกำหนด (early settlement)

### อยู่นอกขอบเขต (Out of Scope) — สำหรับรอบการเรียนนี้
- เชื่อมต่อ Credit Bureau / eKYC / OTP จริง
- Payment gateway จริง, การตัดบัญชีอัตโนมัติ
- การติดตามหนี้ (collection), การปรับโครงสร้างหนี้
- บัตรเครดิต, สินเชื่อเช่าซื้อ, วงเงินหมุนเวียน
- Multi-currency (ใช้ THB อย่างเดียว)

## 3. ผู้ใช้งาน (Actors)

| Actor | คำอธิบาย |
|-------|----------|
| **Applicant** | ผู้สมัครสินเชื่อ กรอกและยื่นใบสมัคร ดูสถานะ |
| **Loan Officer** | เจ้าหน้าที่พิจารณา อนุมัติ/ปฏิเสธ และสั่งเบิกจ่าย |
| **Operations** | บันทึกการชำระเงิน และดำเนินการปิดบัญชี |
| **System** | คำนวณคะแนน/วงเงิน/ตารางผ่อน และบังคับ business rule อัตโนมัติ |

> ผู้ใช้ที่เป็นคน (Applicant, Loan Officer, Operations) ทำงานผ่าน **Web** เสมอ ส่วน business logic และ "System" ทั้งหมดอยู่หลัง **API** — Web ไม่ถือ business rule เอง แต่เรียกผ่าน API

## 5. กฎธุรกิจ (Business Rules) — ค่าสมมติทั้งหมด

> ⚠️ ตัวเลขทั้งหมดกำหนดขึ้นเพื่อการสอน ปรับได้อิสระในห้องเรียน

**BR-01 คุณสมบัติผู้สมัคร**
- อายุ 20–60 ปี
- รายได้ต่อเดือน ≥ 15,000 บาท
- อายุงานปัจจุบัน ≥ 4 เดือน

**BR-02 ความสามารถในการชำระ (DTI)**
- Debt-to-Income หลังรวมงวดใหม่ ต้อง ≤ 70% ของรายได้ต่อเดือน
- สูตร: `DTI = (ภาระหนี้เดิมต่อเดือน + งวดใหม่โดยประมาณ) / รายได้ต่อเดือน`

**BR-03 วงเงินสูงสุด**
- วงเงินอนุมัติสูงสุด = 5 เท่าของรายได้ต่อเดือน และไม่เกิน 1,000,000 บาท

**BR-04 เงื่อนไขสินเชื่อ**
- จำนวนเงินกู้: 10,000 – 1,000,000 บาท
- จำนวนงวด: 6 – 60 งวด (รายเดือน)
- อัตราดอกเบี้ย: แบบลดต้นลดดอก 25% ต่อปี (สมมติ ภายใต้เพดานที่กฎหมายกำหนด)

**BR-05 การให้คะแนน (Credit Band — สมมติ)**
- Band A: ผ่านทุกเกณฑ์ + DTI ≤ 50% → **อนุมัติอัตโนมัติได้** (ยังต้องให้เจ้าหน้าที่ยืนยัน)
- Band B: ผ่านเกณฑ์ + DTI 50–70% → **ส่งเจ้าหน้าที่พิจารณา**
- Band C: ผิดเกณฑ์ข้อใดข้อหนึ่ง → **ปฏิเสธ** พร้อมเหตุผล

**BR-06 การคำนวณงวดผ่อน (Amortization)**
- งวดผ่อนเท่ากันทุกงวด (EMI): `EMI = P × r × (1+r)^n / ((1+r)^n − 1)`
  - `P` = เงินต้น, `r` = อัตราดอกเบี้ยต่อเดือน (= อัตราต่อปี / 12), `n` = จำนวนงวด
- แต่ละงวดแยกเป็นดอกเบี้ย (ยอดคงเหลือ × r) และเงินต้น (EMI − ดอกเบี้ย)
- งวดสุดท้ายปัดเศษให้ยอดคงเหลือเป็น 0 พอดี

**BR-07 การปิดก่อนกำหนด (Early Settlement)**
- ยอดปิดบัญชี = เงินต้นคงเหลือ + ดอกเบี้ยค้างจ่ายถึงวันที่ปิด + ค่าธรรมเนียมปิดก่อนกำหนด (สมมติ 1% ของเงินต้นคงเหลือ)
- ดอกเบี้ยของงวดในอนาคตที่ยังไม่ถึงกำหนด **ไม่คิด**

## 6. วงจรสถานะ (State Machine)

**LoanApplication**
```
Draft → Submitted → UnderReview → Approved → Disbursed
                         └──────→ Rejected
```
- เปลี่ยนสถานะได้ผ่าน method บน Aggregate เท่านั้น (เช่น `Submit()`, `Approve()`, `Reject()`, `Disburse()`)
- `Disburse()` สร้าง **LoanAccount** ใหม่

**LoanAccount**
```
Active → Closed
```
- ปิดได้เมื่อชำระครบทุกงวด หรือปิดก่อนกำหนดสำเร็จ

## 7. Functional Requirements (Epic → User Story → Acceptance Criteria)

> รูปแบบ AC เป็น Given-When-Then เพื่อให้ QA แปลงเป็น test scenario ได้ตรง (W8)
> `[M]` = Must, `[S]` = Should, `[C]` = Could

### Epic 1 — ยื่นใบสมัคร (Loan Application)

**US-01 [M] สร้างและบันทึกใบสมัครแบบร่าง**
_ในฐานะ Applicant ฉันต้องการกรอกข้อมูลและบันทึกร่างใบสมัคร เพื่อกลับมาแก้ต่อได้_
- **Given** ผู้สมัครกรอกข้อมูลส่วนตัวและรายได้ **When** กดบันทึกร่าง **Then** ระบบสร้าง LoanApplication สถานะ `Draft`
- **Given** ยังกรอกไม่ครบ **When** บันทึกร่าง **Then** อนุญาตให้บันทึกได้ (ยังไม่ตรวจ business rule เต็ม)

**US-02 [M] ยื่นใบสมัคร**
_ในฐานะ Applicant ฉันต้องการยื่นใบสมัคร เพื่อเข้าสู่การพิจารณา_
- **Given** ใบสมัครกรอกครบ (ชื่อ อายุ รายได้ อายุงาน จำนวนเงินกู้ จำนวนงวด) **When** กดยื่น **Then** สถานะเปลี่ยนเป็น `Submitted` และล็อกการแก้ไข
- **Given** ข้อมูลไม่ครบ **When** กดยื่น **Then** ระบบปฏิเสธพร้อมระบุ field ที่ขาด และคงสถานะ `Draft`
- **Given** จำนวนเงินกู้/งวด อยู่นอกช่วง BR-04 **When** กดยื่น **Then** ระบบแจ้ง error และไม่เปลี่ยนสถานะ

### Epic 2 — ประเมินสินเชื่อ (Credit Assessment)

**US-03 [M] ประเมินอัตโนมัติเมื่อยื่น**
_ในฐานะ System ฉันต้องประเมินใบสมัครตามกฎ เพื่อจัด Credit Band_
- **Given** ใบสมัครถูกยื่น **When** ระบบประเมิน **Then** สร้าง CreditAssessment ที่มีคะแนน, Band (A/B/C), วงเงินที่อนุมัติได้ และเหตุผล
- **Given** ผิด BR-01 (คุณสมบัติ) **When** ประเมิน **Then** ได้ Band C พร้อมเหตุผล และสถานะใบสมัครพร้อมถูกปฏิเสธ
- **Given** DTI > 70% (BR-02) **When** ประเมิน **Then** ได้ Band C
- **Given** ผ่านทุกเกณฑ์และ DTI ≤ 50% **When** ประเมิน **Then** ได้ Band A และสถานะเป็น `UnderReview`

**US-04 [S] แสดงเหตุผลการประเมิน**
_ในฐานะ Loan Officer ฉันต้องการเห็นเหตุผลของคะแนน เพื่อประกอบการตัดสินใจ_
- **Given** มี CreditAssessment **When** เปิดดูใบสมัคร **Then** เห็นรายการเกณฑ์ที่ผ่าน/ไม่ผ่าน และวงเงินสูงสุดตาม BR-03

### Epic 3 — อนุมัติ (Approval Workflow)

**US-05 [M] อนุมัติใบสมัคร**
_ในฐานะ Loan Officer ฉันต้องการอนุมัติใบสมัครที่ผ่านเกณฑ์_
- **Given** ใบสมัครสถานะ `UnderReview` **When** เจ้าหน้าที่กดอนุมัติ **Then** สถานะเปลี่ยนเป็น `Approved` พร้อมบันทึกผู้อนุมัติและเวลา
- **Given** วงเงินที่ขอ > วงเงินอนุมัติได้ (BR-03) **When** อนุมัติ **Then** ระบบเตือนและให้ปรับวงเงินก่อนอนุมัติ

**US-06 [M] ปฏิเสธใบสมัคร**
_ในฐานะ Loan Officer ฉันต้องการปฏิเสธพร้อมเหตุผล_
- **Given** ใบสมัครสถานะ `UnderReview` หรือ Band C **When** กดปฏิเสธพร้อมระบุเหตุผล **Then** สถานะเปลี่ยนเป็น `Rejected` (final)
- **Given** ใบสมัคร `Rejected` แล้ว **When** พยายามอนุมัติ **Then** ระบบปฏิเสธการกระทำ (invalid transition)

### Epic 4 — เบิกจ่ายและเปิดบัญชี (Disbursement)

**US-07 [M] เบิกจ่ายและสร้างบัญชีสินเชื่อ**
_ในฐานะ Loan Officer ฉันต้องการสั่งเบิกจ่ายเพื่อเริ่มสัญญา_
- **Given** ใบสมัครสถานะ `Approved` **When** สั่งเบิกจ่าย **Then** สถานะเปลี่ยนเป็น `Disbursed` และสร้าง LoanAccount สถานะ `Active`
- **Given** สร้าง LoanAccount **When** เบิกจ่ายสำเร็จ **Then** ระบบสร้าง RepaymentSchedule ตาม BR-06 ทันที
- **Given** ใบสมัครยังไม่ `Approved` **When** สั่งเบิกจ่าย **Then** ระบบปฏิเสธ

### Epic 5 — ตารางผ่อน (Repayment Schedule)

**US-08 [M] คำนวณตารางผ่อนลดต้นลดดอก**
_ในฐานะ System ฉันต้องสร้างตารางผ่อนที่ถูกต้อง_
- **Given** เงินต้น P, อัตรา, จำนวนงวด n **When** สร้างตาราง **Then** ได้ n งวด แต่ละงวดมี ยอดต้น/ดอกเบี้ย/ยอดคงเหลือ
- **Given** ตารางถูกสร้าง **When** รวมเงินต้นทุกงวด **Then** เท่ากับเงินต้นตั้งต้นพอดี (งวดสุดท้ายปัดเศษ)
- **Given** ยอดคงเหลือหลังงวดสุดท้าย **When** ตรวจสอบ **Then** เท่ากับ 0

**US-09 [S] ดูตารางผ่อน**
_ในฐานะ Applicant ฉันต้องการดูตารางผ่อนของบัญชีตัวเอง_
- **Given** บัญชี `Active` **When** เปิดดู **Then** เห็นตารางผ่อนทั้งหมดพร้อมสถานะแต่ละงวด (จ่ายแล้ว/ค้าง)

### Epic 6 — รับชำระ (Payment)

**US-10 [M] บันทึกการชำระรายงวด**
_ในฐานะ Operations ฉันต้องการบันทึกการชำระ_
- **Given** บัญชี `Active` มีงวดค้าง **When** บันทึก Payment ตรงจำนวนงวด **Then** งวดนั้นสถานะ `Paid` และยอดคงเหลือลดลง
- **Given** ชำระน้อยกว่ายอดงวด **When** บันทึก **Then** ระบบแจ้งว่าไม่ครบงวด และไม่ปิดงวด (สมมติ: ไม่รับชำระบางส่วน)
- **Given** ชำระครบทุกงวด **When** บันทึกงวดสุดท้าย **Then** บัญชีเปลี่ยนเป็น `Closed`

### Epic 7 — ปิดก่อนกำหนด (Early Settlement)

**US-11 [S] คำนวณและปิดบัญชีก่อนกำหนด**
_ในฐานะ Applicant ฉันต้องการปิดบัญชีก่อนกำหนด_
- **Given** บัญชี `Active` **When** ขอยอดปิดบัญชี **Then** ระบบคำนวณตาม BR-07 (เงินต้นคงเหลือ + ดอกค้าง + ค่าธรรมเนียม)
- **Given** ชำระยอดปิดบัญชีครบ **When** บันทึก **Then** บัญชีเปลี่ยนเป็น `Closed` และงวดที่เหลือถูกยกเลิก

### Epic 8 — แดชบอร์ด (Dashboard)

**US-12 [C] ภาพรวมสถานะ**
_ในฐานะ Loan Officer ฉันต้องการเห็นภาพรวม เพื่อจัดลำดับงาน_
- **Given** มีใบสมัครหลายสถานะ **When** เปิดแดชบอร์ด **Then** เห็นจำนวนแยกตามสถานะ (Submitted/UnderReview/Approved/Active/Closed)

### Epic 9 — แยก Web + API (ข้อกำหนดเชิงสถาปัตยกรรม)

> business logic และกฎทั้งหมด (Epic 1–8) ต้องอยู่ฝั่ง API ส่วน Web เป็นเพียง client ที่เรียกใช้

**US-13 [M] API ให้บริการทุกความสามารถ**
_ในฐานะ Web ฉันต้องเรียกใช้ทุก use case ผ่าน API เพื่อไม่ต้องถือ business logic เอง_
- **Given** ความสามารถใดๆ ใน Epic 1–8 **When** Web ต้องใช้งาน **Then** มี API endpoint รองรับ และ business rule ถูกบังคับที่ฝั่ง API เสมอ
- **Given** เรียก API ด้วยข้อมูลที่ผิด business rule **When** ประมวลผล **Then** API ปฏิเสธพร้อมรหัส/ข้อความ error ที่ชัดเจน (ไม่พึ่งการ validate ของ Web เพียงอย่างเดียว)

**US-14 [M] Web เป็น client ที่ไม่ถือกฎธุรกิจ**
_ในฐานะผู้ควบคุมการผลิต ฉันต้องการให้ Web แยกจาก API เพื่อเปลี่ยน/ทดสอบแต่ละส่วนได้อิสระ_
- **Given** Web แสดงผลและรับ input **When** ต้องตัดสินใจเชิงธุรกิจ (เช่น อนุมัติได้ไหม, วงเงินเท่าไร) **Then** Web เรียก API เท่านั้น ไม่คำนวณเอง
- **Given** API ปิดให้บริการ **When** เปิด Web **Then** Web แสดงสถานะข้อผิดพลาดอย่างเหมาะสม (ไม่ crash)

**US-15 [S] สัญญาของ API ชัดเจน (API Contract)**
_ในฐานะผู้ทดสอบ ฉันต้องการเอกสาร/สัญญา API ที่ทดสอบได้_
- **Given** API พร้อมใช้งาน **When** เปิดดูสัญญา **Then** มีคำอธิบาย endpoint, request/response schema (เช่น OpenAPI) ที่ใช้ทดสอบและอ้างอิงได้
- **Given** request/response **When** ตรวจสอบ **Then** ตรงตาม schema ที่ประกาศไว้

**US-16 [C] แยกการยืนยันตัวตนระหว่าง Web กับ API**
_ในฐานะระบบ ฉันต้องการให้ Web เรียก API แบบมี token (จำลอง)_
- **Given** Web เรียก API **When** ส่ง request **Then** แนบ token จำลอง และ API ตรวจสอบก่อนให้บริการ (auth จริงอยู่นอกขอบเขต)

## 8. Non-Functional Requirements (ย่อ)

- **ความถูกต้องของการเงิน:** จำนวนเงินเป็นชนิดข้อมูลที่แม่นยำ (ไม่ใช้ floating point) ปัดเศษสม่ำเสมอทั้งระบบ
- **ตรวจสอบย้อนหลัง:** ทุกการเปลี่ยนสถานะบันทึกผู้กระทำและเวลา
- **ความปลอดภัย:** ตรวจสอบ input ทั้งฝั่ง Web และฝั่ง API (API เป็นด่านสุดท้ายเสมอ); ไม่เก็บข้อมูลอ่อนไหวจริง
- **สถาปัตยกรรม:** business logic อยู่ที่ฝั่ง API และรวมศูนย์อยู่ในชั้น domain (แนวคิด domain-centric / layered) — Web ไม่ทำ business logic
- **การแยก Web + API:**
  - API เป็นแบบ stateless และสื่อสารด้วยรูปแบบมาตรฐาน (เช่น REST/JSON)
  - Web กับ API deploy และทดสอบแยกกันได้อิสระ
  - มีสัญญา API (API contract เช่น OpenAPI) ให้อ้างอิงและทดสอบ
  - ตั้งค่า CORS/Origin ให้ Web เรียก API ได้อย่างถูกต้อง
- **ความเป็นอิสระจากภาษา:** requirement นี้ไม่ผูกภาษา — ทีมเลือกภาษา/เฟรมเวิร์กของ Web และ API ได้อิสระ ตราบใดที่พฤติกรรมตรงตาม Acceptance Criteria

## 9. สมมติฐานและข้อจำกัด (Assumptions)

- ผู้ใช้ล็อกอินแล้ว (ระบบ auth อยู่นอกขอบเขต ใช้ user จำลอง)
- 1 ผู้สมัครมีได้หลายใบสมัคร แต่ 1 ใบสมัครที่ `Disbursed` สร้าง 1 บัญชี
- ข้อมูลภาระหนี้เดิมกรอกด้วยมือ (ไม่ดึงจาก bureau)
- เวลา/วันครบกำหนดใช้แบบรายเดือนตามวันเบิกจ่าย

## 10. เชื่อมต่อสู่ Domain Model (สำหรับ W4)

จาก requirement นี้ คาดว่าจะได้ Aggregate/แนวคิดหลักดังนี้ (ยืนยันจริงใน W4):

| แนวคิด | ชนิด | มาจาก |
|--------|------|-------|
| `LoanApplication` | Aggregate Root | Epic 1–4, state machine |
| `ApplicantProfile` | Value Object / Entity | ข้อมูลผู้สมัคร |
| `CreditAssessment` | Entity ภายใน Application | Epic 2, BR-05 |
| `LoanAccount` | Aggregate Root | Epic 4–7 |
| `RepaymentSchedule` / `Installment` | Entity / Value Object | Epic 5, BR-06 |
| `Payment` | Entity | Epic 6 |
| `Money`, `InterestRate`, `Term` | Value Object | BR-04, BR-06 |

**หน่วยที่ deploy แยกกัน (สำหรับ W5 Architecture):**

| หน่วย | หน้าที่ | หมายเหตุ |
|-------|---------|----------|
| **API** | ถือ domain model + business logic ทั้งหมด และเปิด endpoint ให้เรียกใช้ | เป็นที่อยู่ของ Aggregate/VO ทุกตัวข้างบน |
| **Web** | แสดงผล รับ input และเรียก API | ไม่ถือ business rule เอง |

> Aggregate/Value Object ทั้งหมดอยู่ฝั่ง **API** เท่านั้น — เป็นภาษาอะไรก็ได้ตามที่ผู้เรียนเลือก โดย Claude Code เป็นผู้เขียน ส่วนผู้เรียนกำกับว่าให้สร้างอะไรและตรวจว่าผลตรงกับ Acceptance Criteria
